# Billing, Caching, and Token Economics — Formal Analysis

## The Inference Compute Model

Every LLM inference request has two distinct computational phases:

```
Request: [system prompt] + [conversation history] + [new user message]
                              ↓
Phase 1: PREFILL (process all input tokens in parallel)
  • Compute: O(n²) attention over input sequence
  • Produces: KV cache (key-value pairs for each layer)
  • Speed: limited by compute (FLOPS), not memory bandwidth
  • Typical: 1000-5000 tok/s on modern hardware

Phase 2: DECODE (generate output tokens one at a time)
  • Compute: O(n) attention per token (reads KV cache)
  • Each token depends on all previous tokens
  • Speed: limited by memory bandwidth (reading KV cache)
  • Typical: 20-150 tok/s on consumer hardware
```

**Why this matters for pricing:** Prefill and decode have fundamentally different
costs to the provider:

| Phase | Bottleneck | Cost driver | Duration |
|-------|-----------|-------------|----------|
| Prefill | GPU compute (FLOPS) | Number of input tokens | Short burst (100ms for 1K tokens) |
| Decode | Memory bandwidth (GB/s) | Number of output tokens | Long (seconds, one-at-a-time) |
| KV cache | GPU memory (VRAM) | Holds state between tokens | Entire request duration |

---

## Current Pricing Model (Industry Standard)

All major providers use a **two-rate model**:

```
cost = (input_tokens × price_input) + (output_tokens × price_output)
```

Where `price_output > price_input` because:
- Output tokens are sequential (one-at-a-time, slow, ties up GPU longer)
- Input tokens are parallel (batch-processed, fast)
- Output generation occupies the provider's slot for the full duration

### Example: Anthropic Claude Sonnet Pricing
```
Input:  $3.00 / Mtok
Output: $15.00 / Mtok  (5× more expensive)
Cache read:  $0.30 / Mtok (10× cheaper than fresh input)
Cache write: $3.75 / Mtok (slightly more than input)
```

### Example: OpenAI GPT-4o Pricing
```
Input:  $2.50 / Mtok
Output: $10.00 / Mtok (4× more expensive)
Cached input: $1.25 / Mtok (50% discount)
```

## Formal Billing Model for Inference Exchange

### Base Formula

```
cost(request) = T_in × P_in + T_out × P_out

Where:
  T_in  = number of input tokens (all messages sent to the model)
  T_out = number of output tokens (generated by the model)
  P_in  = provider's price per input token
  P_out = provider's price per output token
```

### With Caching (Three-Rate Model)

```
cost(request) = T_cache_hit × P_cache + T_cache_miss × P_in + T_out × P_out

Where:
  T_cache_hit  = input tokens found in provider's KV cache (no recomputation)
  T_cache_miss = input tokens NOT in cache (must be prefilled)
  T_out        = generated output tokens
  P_cache      = price for cached input (typically 10-50% of P_in)
  P_in         = price for fresh input
  P_out        = price for output

Constraint: T_cache_hit + T_cache_miss = T_in (total input)
```

### On the Minimum Charge

**Current problem:** We charge $0.0001 minimum per request, which means
"hi" costs the same as "summarize this 1000 word document."

**Options:**

| Approach | Pros | Cons |
|----------|------|------|
| **No minimum** (charge actual cost) | Fair, proportional | Spam risk (millions of "hi" requests for free) |
| **Flat minimum** ($0.0001/req) | Prevents spam | Unfair for tiny requests |
| **Per-token only** (no minimum, high precision) | Perfectly fair | Enables gaming (1-token requests as health checks) |
| **Minimum + per-token above** | Prevents spam, fair for larger requests | Small complexity |
| **Per-second slot rental** | Aligns with provider cost (GPU time) | Hard to predict cost upfront |

**Recommended:** Remove the flat minimum. Use micro-USD with enough decimal
places to charge fairly:

```
"hi" → 1 input token + 5 output tokens
cost = (1 / 1M × $0.05) + (5 / 1M × $0.20) = $0.0000001 + $0.000001 = $0.0000011

Store as: 1.1 micro-USD (integer: 1 μ$)
Display as: $0.000001
```

For spam prevention: use **rate limiting** (max requests/minute per key)
instead of minimum charge. A rate limit is more honest than overcharging
tiny requests.

## Caching Design

### What "Caching" Means in Practice

When a consumer has a multi-turn conversation:

```
Turn 1: [system prompt + "Hello"]         → 50 input tokens
Turn 2: [system prompt + "Hello" + response + "How are you?"]  → 100 input tokens
Turn 3: [system prompt + all above + "What's 2+2?"]           → 150 input tokens
Turn 4: [system prompt + all above + response + "Thanks"]     → 200 input tokens
```

Without caching: provider prefills ALL input tokens every turn.
With KV cache: provider reuses the KV cache from the previous turn, only
prefilling the NEW tokens (the response + new message).

```
Turn 1: prefill 50 tokens (no cache yet)
Turn 2: cache hit 50, prefill 50 new  → saved 50 tokens of compute
Turn 3: cache hit 100, prefill 50 new → saved 100 tokens
Turn 4: cache hit 150, prefill 50 new → saved 150 tokens
```

### Cache Locality Problem

In a decentralized exchange, the consumer's next message might go to a
DIFFERENT provider (if the first one is busy or more expensive). That
provider has no cache for this conversation.

**Solution: session affinity (sticky routing)**

```
Consumer sets: "ocip_session_id": "chat-abc123"

Coordinator behavior:
  IF the consumer has an active session
  AND the previous provider is still available
  AND the provider has cache for this session
  THEN route to the same provider (cache hit)
  ELSE route normally (cache miss, new prefill)
```

### Cache-Aware Routing Parameters

Consumer REST API (OCIP extension):

```json
{
  "model": "llama-3-8b",
  "messages": [...],
  "ocip": {
    "preference": "cheapest",
    "min_confidence": "contained",
    "session_id": "chat-abc123",
    "cache_preference": "prefer_cached"
  }
}
```

| Parameter | Values | Behavior |
|-----------|--------|----------|
| `cache_preference` | `"prefer_cached"` | Route to same provider if they have cache (default) |
| | `"require_cached"` | ONLY route to provider with cache (fail if none) |
| | `"no_preference"` | Ignore cache, route purely on price/speed/trust |
| `session_id` | string | Groups requests for cache affinity |

### Provider Cache Reporting

Provider heartbeat includes cache state:

```json
{
  "type": "heartbeat",
  "active_requests": 1,
  "loaded_models": ["llama-3-8b"],
  "cache_sessions": ["chat-abc123", "chat-def456"],
  "cache_tokens": 15000,
  "cache_capacity_tokens": 100000
}
```

Coordinator uses this for routing: "consumer's session chat-abc123 has cache
on provider-2 → route there (even if slightly more expensive)."

### Cache Economics

```
Without cache affinity:
  Turn 1: 50 tokens prefill     → provider charges: 50 × P_in
  Turn 2: 100 tokens prefill    → provider charges: 100 × P_in  (repeat work!)
  Turn 3: 150 tokens prefill    → provider charges: 150 × P_in  (more repeat!)
  Total input cost: 300 × P_in

With cache affinity (same provider):
  Turn 1: 50 tokens prefill     → charges: 50 × P_in
  Turn 2: 50 cache + 50 new     → charges: 50 × P_cache + 50 × P_in
  Turn 3: 100 cache + 50 new    → charges: 100 × P_cache + 50 × P_in
  Total input cost: 150 × P_in + 150 × P_cache

If P_cache = 0.1 × P_in (90% discount):
  Without cache: 300 × P_in
  With cache: 150 × P_in + 15 × P_in = 165 × P_in (45% savings!)
```

### Cache Timeout / Eviction

Providers manage their own KV cache. They report which sessions they have
cached. The coordinator trusts this reporting.

Provider cache behavior:
- **Idle timeout:** If a session has no requests for N minutes, evict it (free memory)
- **LRU eviction:** If cache is full, evict least recently used session
- **Provider reports eviction:** heartbeat stops listing that session_id
- **Coordinator updates routing:** no longer prefers this provider for that session

Typical timeouts:
- 5 minutes for short conversations
- 30 minutes for active sessions
- Provider configurable: `--cache-timeout 300` (seconds)

## Solution Concepts (Options)

### Option 1: Simple Two-Rate (No Caching)

```
cost = T_in × P_in + T_out × P_out
No minimum. Rate limiting for spam prevention.
No session affinity. Every request is independent.
```

- Simplest to implement
- Fair for single-turn requests
- Expensive for multi-turn (consumer pays for repeat prefill)
- No provider incentive to cache

### Option 2: Two-Rate + Session Affinity (Implicit Caching)

```
cost = T_in × P_in + T_out × P_out  (same formula)
Session affinity routes repeat conversations to same provider.
Provider caches internally (their business decision).
Consumer pays the same either way — savings are provider-side efficiency.
```

- Simple billing (same as Option 1)
- Provider benefits from caching (less compute, same revenue)
- Consumer benefits indirectly (lower latency from cache hits)
- No billing complexity

### Option 3: Three-Rate with Cache Discount (Anthropic Model)

```
cost = T_cache_hit × P_cache + T_cache_miss × P_in + T_out × P_out
Provider reports cache hit ratio per request.
Consumer gets a discount for cached tokens.
```

- Most fair (consumer pays for actual compute)
- Complex (need to verify provider's cache claims)
- Provider incentivized to cache (they get paid less for cached tokens but use less compute)
- Verification challenge: how does coordinator know provider actually cached vs lying?

### Option 4: Per-Second Slot Pricing (Compute-Time Based)

```
cost = seconds_occupied × P_per_second + T_out × P_per_token
Provider charges for GPU time, not input token count.
```

- Aligns perfectly with provider cost (GPU time = real cost)
- Consumer pays for what they actually use
- Hard to predict cost upfront (depends on provider speed)
- Fast providers are cheaper (incentivizes efficiency)

---

## Recommendation

**Start with Option 2** (two-rate + session affinity):

1. Simple formula: `T_in × P_in + T_out × P_out`, no minimum
2. Add `session_id` to requests for cache affinity routing
3. Coordinator prefers the same provider for a session (if available/affordable)
4. Provider caches internally — their optimization, not a billing concern
5. Consumer gets faster responses from cache hits (TTFT improvement)
6. No cache verification needed (trust is behavioral — provider who caches gets better TPS)

**Later, evolve to Option 3** when providers want to advertise cache discounts
as a competitive advantage ("my cached input is 90% off!").

### What to Change

```
Current:
  cost = max($0.0001, T_out × P_out + 10 × P_in)  ← hardcoded 10 input tokens, minimum

Proposed:
  cost = actual_T_in × P_in + actual_T_out × P_out  ← no minimum, real counts

New API fields:
  Request:  ocip.session_id, ocip.cache_preference
  Response: usage.input_tokens, usage.output_tokens, usage.cache_hit_tokens

  IF session_id provided AND provider has that session cached → prefer that provider
```

### Pricing Display

```
Provider advertises:
  input:  $0.05 / Mtok
  output: $0.20 / Mtok

Consumer sees per-request cost:
  "Hello" (1 tok in, 5 tok out)     → $0.000001
  500-word doc (200 tok in, 100 out) → $0.000030

```

Store all amounts as integers in **nano-USD** (1 USD = 1,000,000,000 nano-USD)
to avoid floating point issues at small amounts. Display with appropriate

## Cache Reliability (Why Cache Hits Are Not Guaranteed)

Even when routing to the same provider, cache hits are NOT guaranteed. The
coordinator should treat caching as probabilistic, not deterministic.

### Why Cache Misses Happen on the Same Provider

| Reason | What happened | How common |
|--------|--------------|------------|
| Idle timeout | Provider evicted session after N minutes of inactivity | Very common |
| Memory pressure / LRU | Other sessions pushed this one out of cache | Common under load |
| Provider restart | Process restart clears all in-memory KV cache | Occasional |
| Model swap | Provider loaded a different model, clearing all cache | Occasional |
| Context overflow | Conversation exceeded model's context window → reset | Predictable |
| Config change | Provider changed quantization/settings | Rare |

### Cache Lifecycle

```
Turn 1: Cache CREATED (full prefill, store KV pairs)
  │
  │  time passes (0-30 minutes depending on provider config)
  │
  ├── If next request arrives quickly AND same provider:
  │     → Cache HIT (skip prefill, immediate decode)
  │
  ├── If idle too long:
  │     → Cache EVICTED (must re-prefill everything)
  │
  ├── If provider is busy (many other sessions):
  │     → Cache EVICTED by LRU (other sessions needed the memory)
  │
  └── If provider restarts:
        → Cache LOST (all state gone)
```

### Verifying Cache State (Trustless)

The provider reports cache state, but how do we verify it without trust?

**Signal: Time to First Token (TTFT)**

```
Cache hit:  TTFT ≈ 10-50ms   (no prefill needed, just start decoding)
Cache miss: TTFT ≈ 200-2000ms (must prefill all input tokens first)
```

The coordinator measures TTFT for every request. This is an observable,
unfakeable signal:
- Fast TTFT → cache was working → charge cached rate (if using Option 3)
- Slow TTFT → cache missed → charge full input rate

A provider can't fake a fast TTFT without actually having the cache.
The computation time for prefill is proportional to input tokens — you
can't skip it without the cached KV pairs.

**TTFT-Based Billing Verification:**

```
If using three-rate billing (Option 3):
  measured_ttft = time_to_first_token(request)
  expected_ttft_no_cache = T_in / provider_prefill_tps  (e.g. 500 tok / 2000 tps = 250ms)
  
  If measured_ttft < expected_ttft_no_cache × 0.3:
    → Cache hit verified (charge P_cache for cached portion)
  Else:
    → Cache miss (charge P_in for all input tokens)
```

### Provider Cache Reporting Protocol

Provider heartbeat includes current cache state:

```json
{
  "type": "heartbeat",
  "active_requests": 1,
  "loaded_models": ["llama-3-8b"],
  "cache": {
    "sessions": ["chat-abc123", "chat-def456"],
    "total_tokens_cached": 15000,
    "capacity_tokens": 100000,
    "eviction_policy": "lru",
    "idle_timeout_seconds": 300
  }
}
```

Per-request response includes actual cache state:

```json
{
  "usage": {
    "input_tokens": 500,
    "output_tokens": 50,
    "cache_hit_tokens": 450,
    "cache_miss_tokens": 50,
    "ttft_ms": 35
  }
}
```

### Design Decision: Trust but Verify

- Route based on provider's REPORTED cache state (from heartbeat)
- Verify with TTFT measurement (from observed timing)
- If provider claims cache hit but TTFT is slow → flag discrepancy
- Don't fail the request — just bill accurately based on observed TTFT
- Over time, providers with consistent cache claims get routing preference

## What We're Still Missing (Open Questions)

### 1. Speculative Decoding / Multi-Token Prediction

Some engines (llama.cpp with speculative decoding, MLX with MTP) generate
multiple tokens per step. How does this affect billing?

- Bill by ACCEPTED tokens (what the consumer receives), not speculative attempts
- The efficiency gain is the provider's reward (faster = more requests/hour)

### 2. Batched Requests (Continuous Batching)

Modern inference engines (vLLM, TGI) batch multiple requests and process
them simultaneously. One provider might serve 8 requests at once.

- Billing: each request is billed independently (consumer doesn't know about batching)
- Provider benefit: higher throughput, more revenue per GPU-second
- OCIP concern: multiple consumers' prompts in the same batch → they're in the same
  process memory simultaneously. For Level 2+, the hardening must protect ALL of them.

### 3. Long Context Pricing

Some models support 128K+ context. A 100K input token request is extremely
expensive for the provider (quadratic attention in prefill). Should pricing
be linear or have surcharges for very long contexts?

Options:
- Linear: same $/tok regardless of context length (simple, slightly unfair to provider)
- Tiered: higher $/tok above 32K context (reflects quadratic compute cost)
- Provider choice: let each provider set their own tier structure

### 4. Streaming Cost Commitment

When streaming starts, the consumer is committed to paying for ALL generated
tokens (they can cancel, but tokens already generated are billed). Should
there be a cost preview / estimate before inference starts?

```json
// Consumer could request an estimate first:
POST /v1/chat/completions
{"messages": [...], "ocip": {"estimate_only": true}}

Response:
{"estimated_cost": {"min": 0.000050, "max": 0.000200, "model": "llama-3-8b"}}
```

### 5. Failed Requests

If the provider crashes mid-inference (returns partial response):
- Bill for tokens actually delivered? (partial bill)
- Bill nothing? (provider ate the compute cost)
- Current: bill for what was delivered, since consumer received value

### 6. Prompt Token Counting — Who Counts?

Options:
- **Coordinator counts** before sending (using tiktoken/tokenizer): accurate, but adds latency
- **Provider reports** after inference: simpler, but relies on provider honesty
- **Both count, compare**: belt-and-suspenders verification

For OCIP with E2E encryption: the coordinator CAN'T count tokens (it can't read
the plaintext messages). So either:
- Count on the consumer side (client SDK reports token count)
- Trust the provider's report
- Use message byte length as a proxy (imperfect but close enough for billing)

### 7. Multi-Modal (Images/Audio)

Vision models charge differently for image tokens (more compute per token).
Need to account for image resolution → token count mapping. Not urgent for
text-only MVP but worth noting.
